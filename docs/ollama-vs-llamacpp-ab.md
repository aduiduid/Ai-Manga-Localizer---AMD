# Ollama 与 llama.cpp 去留对比测试报告

测试日期：2026-11-09　被测版本：0.10.0（过程中修复的两个缺陷见文末，已提交 0.10.1）

> **0.10.3 更新**：本报告第三节的「日文页 llama 少认 3/12 个单元」已被修复。根因是 llama.cpp 在整页级提案阶段一个框都不提（Ollama 的 12/12 来自 15 个网格状瞎猜框撞中真实墨迹后由 Paddle 复核），加上它的 `score` 恒为 `-0.0126953125` 被 0.72 门限全否决。0.10.3 用 `scores_are_informative()` + `ink_tile_hints()` 补上，日文页连跑三次均为 **12 单元**、无丢失，英文 5 页逐单元零变化。但其中两个位置的读数被 Paddle 读成 `ハア`／`な`，且那个 27×26 px 的 `びっ` 仍然检不出 —— **速度（2.9×）与读数精度的差距仍在，本文的双轨制结论不变**。

## 一、结论（先看这里）

| 问题 | 结论 |
| --- | --- |
| 能不能彻底卸载 Ollama？ | **能卸载守护进程（程序本体 120 MB），但省不出磁盘**：9.7 GB 的模型 blob 就是 llama.cpp 正在用的权重，必须保留 |
| 卸载后 llama.cpp 还跑得起来吗？ | **能**。实测杀掉 `ollama.exe`（11434 端口关闭）后，视觉 OCR 仍正常出 4 个框、13.0 s |
| 两条路性能差多少？ | **西文密集页几乎打平**（端到端 1873 s vs 1896 s，最密页反而 llama 快 7%）；**日文竖排页 llama 慢 2.9×**（107.8 s vs 313.7 s） |
| 质量一致吗？ | 西文页**几何 100% 一致**（bbox IoU 全 1.0），但有 12 处 `artwork_text`/`sfx` 判定分歧，净少翻 3 条；日文页 llama **少认 3/12 个单元** |
| 显存差多少？ | llama.cpp 峰值 **8133 MB** vs 守护进程 **9167 MB**，省约 **1.0 GB** |

**建议**：

1. **只为了"少一个常驻程序"** → 可以卸载 Ollama，保留 `ollama-models` 目录，UI 里 OCR 与推理都选 llama.cpp。收益是 120 MB 程序 + 不再有后台守护进程与自动预加载；**磁盘不省**。
2. **想要两条路都最稳（我推荐）** → 保持现状。日常西文书用 llama.cpp（等价、省 1 GB 显存、无守护进程），**日文竖排页仍交给 Ollama**（召回 12/12 vs 9/12，速度快 2.9×）。
3. **什么时候才能把 Ollama 连模型一起删掉** → 等日文竖排的召回追平。差异已定位为 **VLM 判定差异**（不是传输层、不是几何层），需要单独优化；不能接受 3/12 漏字就别删。

## 七、Ollama 仍不可替代的场景

1. **日文竖排 / 手写小字的召回**：12/12 vs 9/12（少 3 个反应拟声词），且同页慢 2.9×。
2. **同页 OCR 速度**（竖排页 2.9×）。
3. **换模型最省事**：`ollama create` / `ollama pull` 一步到位；llama.cpp 要手工放 GGUF 并改模型名。
4. **纯视觉 OCR 模式的框质量**：两边都该用 hybrid，所以这条只是"如果非要用纯视觉"。

反过来，llama.cpp 的优势很实在：**显存省约 1.0 GB**、没有常驻守护进程、上下文/KV 参数完全可控（`-c 65536 -ctk q8_0 -ctv q8_0`）、批次结束进程归零（已实测）。

## 八、过程中发现并修复的两个真实缺陷（已提交 0.10.1）

1. **llama.cpp 视觉调用超时不随预算升级，且重试缺少重复惩罚** —— B 组第一次跑最密页 `00000061` 时在 300 s 处 `timed out` 崩溃，而同一页 A 组能跑完。根因：Ollama 适配器用 `max(self.timeout, ollama_timeout(budget))` 让等待随预算放大、并在重试时加 `repeat_penalty=1.3`；llama 适配器写死 300 s，导致"生成刚好在超时时达到预算"时**永远等不到那次扩容重试**。修复后 B 组跑完该页用 580.1 s。
2. **检测提示词的 JSON 示例写着 `"score":0.0`** —— llama.cpp 把 schema 编译成约束解码语法，会把示例里的边界值原样抄回来，于是**每个框的置信度都是 0.0**，静默关闭下游 score 门限（`prefer_semantic_ocr` 需要 ≥0.72）。示例改为 `0.9` 后，同一个 daemonless 测试返回 0.91–0.95 的真实分值。

> 修复后复跑 B-ja 确认：日文页仍是 9 个单元（说明该页的差距来自 VLM 判定差异，与上面两个缺陷无关，不是传输层问题）。

## 九、复现方式

四组跑完后，临时夹具与装置脚本已清理（`_home\tmp\ab-final` 与 `ab_harness.py` / `ab_compare.py` / `ab_probe_analyze.py` / `ab_gpu.ps1` 均已删除），要复跑需按下面的做法重建：

1. 从被测书里各复制 5 页 / 1 页到临时目录（注意别动原书）。
2. 冷启动：ollama 组先 `release_ollama_model()` 卸掉全部模型，llama 组先 `stop_llama_servers()` 并杀掉残留进程；删掉输出里的 `.manga-localizer-work`。
3. 用 `LocalizerPipeline(paths).run(request, callback)` 直接跑（**不要打 `/api/settings`**，会覆盖用户设置），`PipelineRequest` 以 `UserSettings.load()` 为基，只覆盖 backend/ocr/source_language。
4. **必须复刻 `start.bat` 的环境变量**：漏设 `MLS_HY_MT2_OLLAMA=hy-mt2-1.8b:q8` 会让质量档的候选翻译从 GPU 掉到 torch CPU（2 页就耗 16 分钟）。
5. 单页耗时靠配对回调里的 `识别 <file>` / `已识别 <file>` 两个事件；显存按 `\GPU Process Memory(*)\Dedicated Usage` 每 2 s 采样，并按进程 exe 路径区分「Ollama 自带 runner」与「本项目 stage 的 runner」（两者进程名都叫 `llama-server`）。
